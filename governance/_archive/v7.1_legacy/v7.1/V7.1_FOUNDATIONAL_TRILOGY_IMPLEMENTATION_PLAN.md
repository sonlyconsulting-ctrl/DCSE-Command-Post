### V7 Completion Loop Application

#### Phase 1: BASELINE (Required Before Any Code Change)
Record:
- Local files and paths
- SHA-256 hashes of all poller-related files
- Git branch and commit SHA
- Windows Task Scheduler configuration
- Poller process status
- Last heartbeat timestamp
- Last task claim record
- Supabase records (task queue, heartbeat table)
- Known failure reproduction steps
- Classification: RETAIN / WRAP / REFACTOR / REPLACE

**Status Gate:** No code change permitted until baseline complete.

#### Phase 2: IMPLEMENT
Permitted repairs only (no replacement unless contract amended):
- Obsolete temporary allowlist
- Incorrect local path
- Broken scheduler command
- Missing environment discovery
- Lease or duplicate-claim defect
- Heartbeat failure
- Bounded retry defect

**Status Gate:** Implementation limited to proven defects.

#### Phase 3: VERIFY LOCALLY
Acceptance suite (all must pass):
1. Imports succeed
2. Audit-only mode succeeds
3. Unauthorized packets do not execute
4. Authorized test packet reaches correct state sequence
5. Receipt contains correct task ID and source hash
6. Re-running same task produces idempotent skip
7. Expected outputs verified
8. Duplicate task claims do not occur
9. Poller restart recovers cleanly
10. GitHub and Supabase remain available if poller stops
11. No legacy `git add .` or automatic push activated
12. No production change occurs

**Status Gate:** `IMPLEMENTED_PENDING_REVIEW`

#### Phase 4: SUBMIT EVIDENCE
Create draft PR with:
- Commit SHA
- Changed files with exact reasons
- Test commands and results
- Scheduler evidence
- Heartbeat evidence
- Rollback procedure
- Unresolved risks
- Artifact hashes

Update Supabase task record with PR reference.

**Status Gate:** `REVIEW_REQUESTED`

#### Phase 5: INDEPENDENT REVIEW (Claude Code)
Claude verifies:
- Repair contract compliance
- No unauthorized new poller
- No secret exposure
- No lane violation
- Acceptance tests passed
- Idempotency confirmed
- Rollback viability
- GitHub/Supabase evidence reconciliation

**Disposition Options:**
- `APPROVE`
- `APPROVE_WITH_CORRECTIONS`
- `REJECT`
- `INSUFFICIENT_EVIDENCE`

**Status Gate:** `INDEPENDENTLY_VERIFIED` or `CORRECTIONS_REQUIRED`

#### Phase 6: DCS APPROVAL

```

```

```
→ BOW-003 released

→ automatically promoted

```

**Mandatory Stops Requiring DCS Level 0:**
Automatic approval stops only if any of these occur:
- Critical security vulnerability
- Production-data risk or destructive change
- PS, SC, TSL, or other lane conflict
- Missing or conflicting canonical repository
- Material architecture replacement
- New paid service or material expense
- Public or production deployment
- Reviewer returns `REJECT` or `INSUFFICIENT_EVIDENCE`
- Confidence falls below the required threshold (90%)
- Evidence in GitHub and Supabase does not reconcile

Minor, moderate, and easily correctable findings return automatically to the executor for repair, retest, and rereview. They do not return to DCS Level 0.
