# DCSE V7.1 Strategic Model and Agent Participation Standard

Status: IMMEDIATE CONTROLLED USE
Authority: DCS
Scope: All approved AI models, agents, runtimes, and review systems
Confidentiality: INTERNAL

## 1. Decision

DeepSeek, Grok, Gemini, Antigravity, MiniMax, and future approved systems are included under the same universal onboarding, discovery, access, evidence, and lane controls as ChatGPT, Claude, Coder, Codex, Qwen, and Copilot.

No model receives authority merely because it is added to the registry. Participation is capability-based, task-bounded, evidence-scored, and revocable.

## 2. Participation Classes

### Frontier reasoning and architecture

Potential participants:

- ChatGPT
- Claude
- Gemini
- Grok

Typical use:

- architecture
- strategy
- complex synthesis
- multimodal review
- red-team analysis
- independent review

### Coding and implementation

Potential participants:

- Coder
- Codex
- Claude Code
- DeepSeek Coder
- Gemini coding agents
- Qwen Coder

Typical use:

- repository audit
- bounded implementation
- tests

- refactoring

- evidence manifests

### Cost-efficient and high-volume work

Potential participants:

- DeepSeek
- MiniMax
- Qwen
- local Ollama models
- approved smaller Gemini or OpenAI models

Typical use:

- classification
- extraction
- summarization
- first-pass code review
- document chunking
- structured research intake
- test generation

### Media, voice, and interactive experience

Potential participants:

- MiniMax
- Gemini
- approved video, voice, image, and game-generation systems

Typical use:

- media prototypes
- voice and video workflows
- interactive experiences
- game and quiz content
- multimodal product demonstrations

## 3. Registry Fields

Each approved participant must have a profile containing:

- provider and model or agent identifier
- access method
- deployment environment
- supported tools
- context limits
- pricing or infrastructure cost
- privacy classification
- data-retention position
- licensing restrictions
- verified task strengths
- verified weaknesses
- allowed lanes
- prohibited lanes
- token or runtime ceiling
- review requirement
- last calibration date
- current status

Statuses:

- CANDIDATE
- TESTING
- PILOT
- APPROVED
- RESTRICTED
- SUSPENDED
- RETIRED

## 4. Universal Controls

Every participant must:

1. complete the universal onboarding and access gate;
2. load the canonical discovery manifest;
3. verify GitHub and applicable Supabase access;
4. declare lane and role;
5. use scoped negative findings;
6. preserve artifact identity and traceability;
7. operate within assigned tools and budgets;
8. provide evidence and uncertainty;
9. avoid self-promotion or self-approval;
10. submit outputs for risk-appropriate verification.

## 5. Task Assignment Rule

Model selection must be based on:

- task type
- risk
- privacy
- tool access
- prior verified performance
- context requirement
- cost
- latency
- licensing
- availability

Brand preference alone is not a valid routing rule.

Primary operational metric:

`cost per verified accepted requirement`

Supporting metrics:

- acceptance rate
- correction rate
- reviewer time
- token or compute cost
- latency
- defect escape rate
- evidence completeness

## 6. Strategic Inclusion Decisions

### DeepSeek

Include as a strategic coding, reasoning, and cost-comparison candidate. Require license, hosting, privacy, and task-specific calibration before approval.

### Grok

Include as a strategic research, current-information, alternative-analysis, and coding candidate where connector and data-handling controls are verified.

### Gemini

Include as a strategic multimodal, long-context, Google-ecosystem, coding, and independent-review candidate.

### Antigravity

Include as a named candidate pending exact product identity, capability verification, access method, license, and security review. No assumptions may be made from the name alone.

### MiniMax

Include as a strategic media, voice, video, long-context, interactive-experience, and cost-comparison candidate subject to product-specific evaluation.

## 7. Minimum Calibration Packet

Before a participant becomes APPROVED for a task class, run:

1. three representative tasks;
2. one known-failure or adversarial task;
3. one evidence and citation test;
4. one tool-access and permission test;
5. one token or cost measurement;
6. one independent review;
7. one lane-isolation check.

## 8. Promotion and Removal

DCS authorizes participation status. Agents may recommend status changes but may not approve themselves or other models.

A participant may be restricted or suspended for:

- false completion claims
- repeated unscoped negative findings
- secret exposure
- lane violation
- unreliable tool reporting
- unacceptable rework
- license or privacy changes
- cost or availability deterioration

## 9. Immediate Use

The named systems may enter CANDIDATE or TESTING status immediately. They may receive bounded non-destructive work after successful onboarding. Production, destructive, public, security, database, and promotion actions require the governing approval and review gates.
