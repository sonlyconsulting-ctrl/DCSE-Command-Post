# DCSE V7.1 Owned Product Harness Build Plan

Status: DRAFT FOR DCS REVIEW
Authority: V7 extension, not V8 replacement
Owner: DCS
Confidentiality: INTERNAL

## 1. Decision

DCSE will develop an owned, marketable product harness that governs product discovery, requirements, model routing, agent orchestration, evidence, review, promotion, lessons learned, and durable enterprise memory.

This is designated V7.1 because it operationalizes existing V7 principles without replacing the constitutional identity, lane firewall, promotion authority, or Structure Precedes Scale doctrine. A future V8 should be reserved for a fundamental change in authority, identity, or governance model.

## 2. Commercial Product Concept

Working name: DCSE Governed Product Factory

Marketable capabilities:

1. Product and requirements registry
2. Replaceable model gateway
3. Agent role orchestration
4. Context manifests and token controls
5. Evidence-based completion
6. Independent review and promotion
7. Product memory and lessons learned
8. Website and web-application build templates
9. Interactive quiz and game modules
10. Client-facing project visibility

The commercial proposition is not generic AI app generation. The product provides governed, traceable, model-neutral delivery from idea through production readiness.

## 3. Non-Destructive Migration Rule

Existing work is presumed valuable until evidence supports another classification.

Every component must be classified:

- RETAIN: functioning and aligned
- WRAP: functioning but requires standardized interfaces, logging, governance, or routing
- REFACTOR: valuable but structurally incomplete
- REPLACE: unsafe, materially defective, or incompatible

No rewrite is authorized solely because a newer framework appears cleaner.

## 4. V7.1 Control Modules

### V7.1-PB Product Build Control

Defines capability packets, requirements, acceptance criteria, evidence, and promotion.

### V7.1-MR Model Routing and Calibration

Routes tasks by task class, risk, context need, cost, privacy, tool use, and prior verified performance.

Primary performance metric: cost per verified accepted requirement.

### V7.1-AO Agent Orchestration

Minimum production pattern:

1. Planner
2. Builder
3. Verifier

High-risk additions:

4. Security reviewer
5. Architecture reviewer
6. Promotion authority

### V7.1-RI Research Intelligence

Controls transcript intake, claim extraction, verification, applicability, and Adopt/Pilot/Watch/Reject disposition.

### V7.1-SLG Self-Learning Governance

Projects may generate governance-change candidates, but no agent may promote its own proposal.

Required flow:

Observation -> Evidence -> Root Cause -> Proposed Control -> Independent Review -> DCS Approval -> Promotion -> Review Date

### V7.1-EM Enterprise Memory

Stores source materials, decisions, product requirements, evidence, model results, lessons learned, and supersession history.

## 5. Initial Product Scope

### Internal pilot 1: TSL Production Readiness Audit

Purpose: reconstruct intended product, implementation, database state, runtime behavior, evidence, and operational readiness.

The audit must produce atomic requirements and classify each as UNKNOWN, ABSENT, DESIGNED, PARTIAL, IMPLEMENTED, VERIFIED, PRODUCTIONAL, or DEFERRED.

### Internal pilot 2: SC Modular Website

Purpose: demonstrate product depth through TSL, Vow and Go, the Product Factory, evidence mode, research, and governed AI concierge.

### Internal pilot 3: SS Interactive Experience

Purpose: validate quizzes, media, storytelling, games, voice, and reusable engagement modules.

## 6. Time-to-Market Controls

The harness must remain thin during the pilot.

Version 1 includes only:

1. Product and requirement registry
2. Task intake and classification
3. Model and agent assignment
4. Context manifest
5. Isolated Git branch or worktree
6. Test execution
7. Evidence manifest
8. Independent review
9. Promotion record
10. Lessons-learned record

Version 1 excludes autonomous self-modification, large agent swarms, automatic production deployment, and wholesale replacement of current tools.

## 7. Open-Source Strategy

Preferred order:

Configure -> Extend -> Wrap -> Narrow Fork Only When Necessary

DCSE-owned strategic layer:

- Governance engine
- Product memory
- Requirements and task contracts
- Model router
- Calibration records
- Evidence schema

Replaceable infrastructure may include Ollama, LiteLLM-compatible routing, OpenHands-style execution, PostgreSQL/Supabase, React/Next.js/Astro, Playwright, GitHub, and modular observability.

## 8. Claude Review Protocol

Claude is designated the external reviewer for this proposal.

Claude may:

- review GitHub files and Supabase registry records
- identify omissions, contradictions, overengineering, security concerns, and time-to-market risks
- propose changes through GitHub review comments

Claude may not:

- merge the pull request
- change governance status
- promote V7.1
- alter Supabase production records without an approved task
- access or introduce PS lane materials

ChatGPT/DCS response workflow:

1. Read Claude comments from GitHub
2. Classify each as ACCEPT, ACCEPT WITH MODIFICATION, DEFER, or REJECT
3. Respond in the same GitHub review thread
4. Update the plan only after DCS direction
5. Preserve the complete review history
